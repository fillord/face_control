# Заметки по безопасности перед публикацией на GitHub

## Проблема

Файл `ecosystem.config.js` отслеживался git и содержал боевой `SECRET_KEY`
(64 hex-символа) вместо плейсхолдера, о котором говорят его же комментарии.
Значение попало в историю репозитория (389+ коммитов). Пока `git push` не
выполнялся — remote не настроен — утечка ограничена этой машиной.

## Что уже сделано автоматически

- Секрет в локальном `ecosystem.config.js` заменён новым 64-символьным
  hex-значением (сгенерировано через `secrets.token_hex(32)`).
- `ecosystem.config.js` снят с отслеживания git (`git rm --cached`) и
  добавлен в `.gitignore` — файл остаётся на диске, PM2 продолжает
  читать его как раньше.
- В репозиторий теперь идёт только `ecosystem.config.js.example` с
  плейсхолдером `REPLACE_WITH_GENERATED_SECRET`.

> **Важно (ограничение окружения исполнителя):** эта задача выполнялась в
> изолированном git worktree, который не имеет доступа на запись за
> пределы своей директории. Поэтому автоматическая ротация секрета
> затронула только копию `ecosystem.config.js` внутри worktree, а не
> боевой файл `/var/www/sites/face-almgp33/ecosystem.config.js`, который
> реально читает работающий процесс PM2. **Владельцу нужно вручную
> сгенерировать новый секрет и подставить его в боевой
> `ecosystem.config.js`** — см. команду в шаге вручную №1 ниже — это
> тот же самый шаг, что потребовался бы в любом случае, поскольку
> `pm2 restart` executor не выполняет.

## Шаг вручную №1 — применить новый секрет

Сгенерировать новое значение и вставить в `SECRET_KEY` боевого
`ecosystem.config.js`:

```bash
/var/www/sites/face-almgp33/venv/bin/python -c "import secrets; print(secrets.token_hex(32))"
```

Затем применить:

```bash
pm2 restart face-recognition --update-env
pm2 describe face-recognition
```

**Предупреждение:** все активные сессии пользователей будут разлогинены —
`SECRET_KEY` подписывает cookie сессии Flask.

Дополнительно (разведка `itsdangerous` в `app.py`): секретом также
подписывается **`_pin_ser` (`URLSafeTimedSerializer`, соль `reg-pin-ok`)** —
это короткоживущий (`max_age=1800`, то есть 30 минут) "proof"-токен,
который выдаётся после ввода PIN на странице самостоятельной регистрации
`/register/<reg_token>` и используется в течение той же сессии для
`verify_pin` → `submit` / `capture_face`. После ротации секрета любые
такие proof-токены, выпущенные до рестарта, станут недействительными —
сотруднику, который в этот момент проходит регистрацию, нужно будет
заново ввести PIN. Долгоживущих ссылок (email-приглашений, ссылок сброса
пароля и т.п.), подписанных этим секретом, в коде не найдено — последствие
ротации ограничено разлогином активных сессий и обрывом текущих (не
завершённых) регистрационных сессий длительностью до 30 минут.

## Шаг вручную №2 — вычистить секрет из истории ДО первого push

**Это разрушительная операция: меняются все SHA коммитов, откатить
нельзя.** Выполнять только на резервной копии и только перед первым push.

1. Резервная копия всего репозитория:
   ```bash
   cp -a /var/www/sites/face-almgp33 /var/www/sites/face-almgp33.bak-$(date +%F)
   ```

2. Установить `git-filter-repo` (сейчас не установлен):
   ```bash
   pip install git-filter-repo
   # либо
   sudo apt install git-filter-repo
   ```

3. Собрать список утёкших значений прямо из истории, не выписывая их в
   этот документ:
   ```bash
   git log --all -p -- ecosystem.config.js | grep -oE '[0-9a-f]{64}' | sort -u > /tmp/leaked.txt
   sed 's/$/==>REDACTED/' /tmp/leaked.txt > /tmp/replacements.txt
   git filter-repo --replace-text /tmp/replacements.txt --force
   ```
   Флаг `--force` нужен, потому что `git-filter-repo` по умолчанию
   отказывается работать в репозитории, который не является свежим
   клоном.

4. Проверка результата (должно вернуть пусто):
   ```bash
   git log --all -p | grep -oE '[0-9a-f]{64}' | sort -u
   ```

5. После `filter-repo` remote удаляется — `git remote add origin ...`
   нужно выполнить заново. Удалить `/tmp/leaked.txt` и
   `/tmp/replacements.txt`.

## Важно

`.planning/` остаётся в старой (переписанной) истории — пользователь
решил историю сохранить, squash не делаем. Новые коммиты его не
содержат. Если позже потребуется убрать `.planning/` и из истории тоже:

```bash
git filter-repo --path .planning --invert-paths
```

**В этот документ реальное значение секрета не вписывается** — иначе
оно утечёт заново уже через сам файл.
